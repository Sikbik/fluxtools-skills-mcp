# PROJECT KNOWLEDGE BASE

## OVERVIEW

This repository contains Flux operational tooling across multiple execution surfaces:

- `flux-mcp/` - the production MCP server and current execution layer
- `claude/flux-cloud/` - Claude skill wrapper and references
- `codex/flux-cloud/` - Codex skill wrapper, references, and scripts
- `fluxos-cli/` - the shell-native CLI package

The repo already has strong MCP coverage. The primary task now is building out `fluxos-cli` as a first-class shell and agent execution surface without duplicating the Flux workflow logic already implemented in `flux-mcp`.

## PRIMARY TASK

Until further notice, `fluxos-cli` is the main focus of this repository.

Primary roadmap:

- `fluxos-cli/ROADMAP.md`

Execution priority:

1. Build `fluxos-cli` as its own package
2. Reuse and extract shared logic from `flux-mcp`
3. Keep MCP and skills stable while shared-core extraction happens
4. Integrate CLI back into MCP and skills only after the CLI is mature

Do not treat the CLI as a second independent implementation of Flux logic.

Use this duplication rule:

- duplicate CLI surface code freely when it improves independence and usability
- avoid duplicating Flux business logic unless it is a deliberate temporary tradeoff

## CONVENTIONS

- `flux-mcp` is TypeScript ESM with strict typing and Node 20+ expectations.
- Generated artifacts live in `dist/` and `flux-mcp/dist/`.
- Endpoint inventories are generated by `codex/flux-cloud/scripts/generate-endpoints.js`.
- `fluxos-cli` should also be built as a TypeScript ESM package unless the roadmap explicitly changes that decision.
- JSON contracts matter more than pretty output for CLI work.
- The CLI should own its own shell-facing concerns:
  - argument parsing
  - command routing
  - stdout and stderr formatting
  - exit codes
  - local persistence
  - help and UX text

## DUPLICATION GUIDANCE

Duplication is allowed when it serves CLI independence.

Good duplication:

- CLI argument parsing
- command routing
- output formatting
- exit code mapping
- config and profile persistence
- local resource persistence
- shell UX conveniences
- lightweight adapters that map CLI inputs to shared execution code

Temporary duplication is acceptable when it unblocks delivery, but it should be tracked for later extraction in `fluxos-cli/ROADMAP.md`.

Duplication to avoid unless there is a documented blocker:

- auth workflow rules
- request safety rules
- mutation gating
- signing payload construction
- registration, update, and renew semantics
- Flux response normalization rules
- endpoint classification rules
- any other logic that defines how Flux behavior actually works

## ANTI-PATTERNS

- Do not duplicate Flux business logic from `flux-mcp` into `fluxos-cli` when shared extraction is feasible.
- Do not edit generated files directly:
  - `dist/*.skill`
  - `flux-mcp/dist/*`
  - `flux-mcp/data/endpoints.json`
  - `codex/flux-cloud/references/endpoints*.{json,md}`
- Do not bypass Flux mutation confirmation rules (`confirm=true` or `allowMutation=true`).
- Do not let CLI convenience commands silently weaken existing MCP safety boundaries.
- Do not wire skills to the CLI before the CLI contracts are stable.

## COMMANDS

```bash
# Build MCP server
cd flux-mcp
npm ci
npm run build

# Test MCP server
cd flux-mcp
npm test

# Package Codex skill
python3 scripts/package_skill.py codex/flux-cloud dist

# Package Claude skill
python3 scripts/package_skill.py claude/flux-cloud dist

# Regenerate endpoint inventory
cd codex/flux-cloud
node scripts/generate-endpoints.js --ref master --also-mcp
```

`fluxos-cli` now builds with `npm --prefix fluxos-cli run build` and tests with `npm --prefix fluxos-cli test`.

## WORKFLOW (RALPH-LOOP)

When implementing roadmap items, follow this loop strictly:

1. Implement one roadmap item, as the smallest shippable slice
2. Run targeted tests or build checks for that slice
3. Mark the roadmap checkbox(es) complete
4. Create a git commit for that slice
5. Move to the next slice

Rules:

- Use `fluxos-cli/ROADMAP.md` as the implementation order for CLI work.
- Never batch multiple roadmap items into a single commit unless they are inseparable.
- Do not pause to ask the user to continue between roadmap slices unless blocked.
- Prefer shared-core extraction over copy-paste when moving domain behavior toward the CLI.
- It is fine to duplicate interface-level CLI code if that keeps the CLI usable and MCP-optional.

## NOTES

- Root workflows live in `.github/workflows/ci.yml` and `release.yml`.
- The upstream Flux repo is not part of this distribution; prefer changes in skill, MCP, and CLI layers unless explicitly asked to work on Flux core.
- For CLI work, prioritize agent-safe JSON output, state visibility, explicit confirmation, and behavior parity with MCP.
